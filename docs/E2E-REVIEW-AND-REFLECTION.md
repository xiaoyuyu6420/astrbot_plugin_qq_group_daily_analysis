### 1.2 但实测暴露了「修复」的真实性质 —— 治标

`fbb97f8`（`CircuitBreaker recovery_timeout=180s`）的修复意图是「避免长时间熔断不恢复」。
**实测**：14:40 触发熔断后，17:09 / 17:12 / 17:24 / 17:53 / 18:14 / 18:29 / 19:03 / 19:18 / 19:34 —— 改完之后**仍持续大面积超时**。

这证明 `recovery_timeout=180` 只是让熔断器「3 分钟后允许重试」，但**底层 LLM provider 本身就在超时**（`Request timed out` / `Connection error`）。熔断器缩短恢复时间 ≠ 解决后端不稳。**这是典型的症状驱动修复（symptom-driven fix）**。

### 2.3 量化证据：修复模式的系统性问题

最近 40 个 commit：`feat:16 / fix:10 / refactor:3 / ci:4 / test:2 / chore:2`。

- **fix 是 refactor 的 3.3 倍** —— 项目处于「加功能 + 补漏」循环，结构性整理严重不足。
- fix 的内容几乎全是**补丁式**：补 CI 依赖（3 次）、补 schema 配置组、补 mock、调熔断参数、改水位线公式。没有一个 fix 是「重构导致」，全是「新功能/外部环境变化暴露的缝」。
- **这是典型的「技术债复利」信号**：每加一个 feat 就埋下若干个未来 fix，因为结构不够稳。

## 第三部分：深刻反思（心理学 + 信息学 + 学习曲线）

### 3.1 心理学视角：为什么会陷入「feat → fix」循环？

**3.1.1 奖励偏差（reward bias）与多巴胺回路**

- 加新功能（feat）会立刻产生**可见反馈**：群里多了一种推送、README 多了一张截图、用户能用。大脑的多巴胺系统对「可展示的成果」给出强奖励。
- 重构（refactor）的反馈是**延迟且不可见**的：代码更清晰、bug 更少——但这些「没发生的事」无法触发奖励回路。心理学上称为 ** omission bias 的反面**：我们高估「做了什么」的价值，低估「避免了什么」的价值。
- **结果**：16 个 feat vs 3 个 refactor。你不是在写更好的代码，你是在**追逐下一个能截图的功能**。

**3.1.2 损失厌恶（loss aversion）与「它还能跑」陷阱**

- 项目能跑通端到端、测试 188 个通过——这制造了**虚假的安全感**。卡尼曼的系统 1 会快速判断「能跑 = 没问题」，让系统 2（审慎分析）懒得启动。
- 但「能跑」和「健康」是两回事。一个 `pytest` 收集就崩的项目，说明**你很久没在自己机器上跑过完整测试了**——你只在服务器上通过日志确认「它还在动」。这是**验证靠观察、不靠断言**的危险模式。

**3.1.3 沉没成本与「再缝一个补丁」**

- `recovery_timeout=180s` 这种修复之所以发生，是因为**在错误的抽象层打补丁比挖根因便宜**（短期）。但每次表层的补丁都在**增加未来的认知负担**：下一个读这段代码的人要理解「为什么是 180 而不是 60」「这个熔断器到底保护什么」。技术债的利息是**以理解成本的形式**支付的。

### 3.2 信息学视角：系统的熵与耦合

**3.2.1 分层失衡 = 信息流向的退化**

```
domain         4018 行 (17%)   ← 应该是核心，却最小
application    4138 行 (18%)
infrastructure 14267 行 (61%) ← 巨型，吞掉了本应属于 domain 的逻辑
shared          551 行 (2%)
```

DDD 的本意是 **domain 拥有业务规则，infrastructure 只是技术细节**。但这里 infrastructure 是 domain 的 3.5 倍——意味着**业务逻辑泄漏进了适配器、报告器、持久层**。这不是 DDD，这是**带命名的文件夹**（folders with names）。

后果（信息论上）：业务规则散落在多个高熵模块里，**修改一处业务行为需要扫描 14000 行基础设施代码**。`message_monitor_service.py`（1369 行）和 `generators.py`（1478 行）是耦合重灾区——它们大概率同时包含「做什么」和「怎么做」。

**3.2.2 配置熵**

`_conf_schema.json` 有 12 个顶层配置组、14+ 个 group。每个配置项都是一条**外部信息输入**。当输入维度超过 7±2（米勒数），人类就无法在心智模型中同时持有所有配置的交互关系。**你大概率已经记不清 `incremental` 和 `message_monitor` 的水位线如何相互影响了**（6e7cb73 的水位线 bug 就是这种遗忘的直接证据）。

**3.2.3 补丁的信息学本质**

每个 fix 都是在**往系统注入特例**（special case）。特例越多，系统的**条件熵**越高，可预测性越低。`fix(muted)` 连续两个 commit（禁言跳过、set_reaction 失败判定禁言）说明「禁言」这个边界条件是**事后发现的**，被缝进了多个调用点，而不是在 domain 层被一次性建模成一等概念。

### 3.3 学习曲线视角：下一个人的灾难

**3.3.1 认知负荷理论（Sweller）**

一个新人理解这个项目，需要同时在工作记忆里持有：
- AstrBot 框架的事件模型（filter/handler/hook）
- OneBot/Telegram/Discord/Lark 四套适配器差异
- 实时监控 vs 定时日报 vs 分类聚合 三条调度路径
- LLM provider 链 + 熔断 + 限流 + 重试 + schema 修复 + 正则降级 六层防御
- 12 组配置的交互

工作记忆容量是 4±1。**这个项目远超单次可理解阈值**，必然导致「只敢改自己熟悉的那一小块」——这是**局部最优陷阱**的制度化根源。

**3.3.2 「上一次修复」暴露的元问题**

`fbb97f8` 调一个魔法数字 180，commit message 是「从服务器同步」。这说明：**你的真实调试发生在服务器上（靠日志），而不是在本地（靠测试和断点）**。学习曲线上，这是**反馈回路过长**——改一行代码 → 推到服务器 → 等定时任务 → 看日志 → 再改。每个循环几小时。人类在反馈延迟 > 15 分钟时，学习效率断崖式下降（这是为什么 TDD 有效的底层原因）。

**这个反馈回路的设计缺陷，比任何一个具体 bug 都重要。**

## 第四部分：重构计划（按 ROI 排序，每项独立可交付）

### 原则

1. **先修反馈回路，再修代码**——反馈回路不修，所有重构都会重蹈「服务器日志调试」的覆辙。
2. **每一步都要可独立合并、可独立回滚**，不做大爆炸式重构。
3. **用测试锁死行为再动结构**——重构前必须有失败可复现的测试。

---

### P0（本周）：修复反馈回路 —— 让「本地验证」重新可能

| 任务 | 动作 | 验收 |
|------|------|------|
| **P0-1 修 R1：删/改 `scripts/test_regional_rendering.py`** | 该脚本依赖已删除的 `QualityReview`。要么删除脚本，要么改为不依赖锐评 model 的渲染测试。 | `pytest`（无参数）能完整收集不报错 |
| **P0-2 修 R2：real_e2e 加 marker 隔离** | 给 `tests/real_e2e/*.py` 加 `@pytest.mark.real_e2e`，在 `pytest.ini`/`pyproject.toml` 配 `addopts = -m "not real_e2e"` 默认排除；CI 里用 `-m real_e2e` 显式启用。 | 本地 `pytest` 默认不触碰 real_e2e；CI 仍能单独跑 |
| **P0-3 加 pre-commit 跑 pytest** | `.pre-commit-config.yaml` 已存在，补一个 hook：提交前跑 `pytest -q`（排除 real_e2e）。让「本地崩溃」在 commit 前就被拦截，而不是推到服务器才发现。 | 故意引入 import 错误时，pre-commit 拒绝提交 |

> **心理学锚点**：P0 不改业务逻辑，只重建「改→验证」的短反馈回路。做完这步，后面所有重构的学习效率提升 3-5 倍。

### P1（2 周内）：治理 LLM 不稳的根因（R3）—— 修信息源，不修熔断器

| 任务 | 动作 | 验收 |
|------|------|------|
| **P1-1 LLM 调用超时分级** | 当前 `Request timed out` 是统一超时。区分：连接超时（短，5s，应快速失败切 provider）、首 token 超时（中，30s）、整体超时（长，按 provider 配置）。 | 服务器日志能区分三类超时；慢 provider 不再拖垮整体 |
| **P1-2 provider 健康度探活** | 在 `_get_circuit_breaker` 旁加轻量健康分（最近 N 次成功率），调度时优先选健康 provider，而不是 fixed primary。 | digest 产出时 LLM 失败率从实测的 ~40% 降到 < 10% |
| **P1-3 JSON 解析失败的归因** | 实测「JSON 修复重试 + 正则降级」反复触发。加结构化日志：记录是 truncation / 引号 / 字段缺失哪种，喂回 prompt 优化。 | schema 修复重试触发率下降；正则降级成为真·兜底而非常态 |

> 治标（调 180s）→ 治本（让 provider 别超时）。熔断器保留，但作为**最后防线**而非第一道关。

## 第五部分：元结论

这个项目**不缺功能，缺的是让功能持续可靠的结构和验证机制**。

- 它现在能跑，是因为你在服务器上一次次手动盯着日志缝补丁。
- 它未来会崩，是因为下一个接手的人（或三个月后的你）无法在本地 5 分钟内验证一个改动。
- `fbb97f8` 调 180 秒这件事本身不重要；重要的是**「为什么你会需要去服务器上调一个魔法数字」**——答案是反馈回路断了。

**P0 做完，你就重新拿回了「在本地 confidently 改代码」的能力。这是后续一切的前提。**
